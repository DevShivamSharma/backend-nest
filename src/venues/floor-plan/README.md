# Floor-plan import

The floor-plan importer is independent of the CSV adapter. The layered CAD/grid engine is reused from backend `origin/main` (f4ed0de), with a source-coordinate adapter and the POC review/save API. PDF.js extracts vector paths and selectable text; OpenCV and bundled English Tesseract handle raster pages; ASCII DXF entities use drawing units when specified. Venue identities, source colours and 1 m grids are not hardcoded. All automatic regions are proposals requiring review.

## User flow

In a venue, use **Add hall → Import from floor plan**. Upload PDF/DXF/PNG/JPEG (20 MB, up to 50 PDF pages). The guided flow is upload, choose halls, review one hall, then save selected halls. A single hall opens review directly. Corrections and advanced tools are available on demand; edits are applied automatically before preview. Every selected hall needs its own visual confirmation, and geometry or scale edits invalidate affected confirmations.

The import tour opens automatically when either import screen loads and can be reopened with **Start import tour**. It includes nine floor-plan topics and five CSV topics, English/Hinglish instructions, an illustrative hall/foyer diagram, context-specific pending actions and **Show on page** navigation. Opening the tour never confirms geometry or saves data. The corrections panel exposes **Shape type** and foyer ownership together, so a wrongly proposed hall can be reclassified as a foyer. Its old hall-specific dimensions are cleared and the affected floor needs review again. Metric square-grid spacing can be corrected while preserving the outline, origin and rotation.

The hall-with-gridded-foyer regression fixture checks that the drawing's prominent plural hall title is recognised, adjacent-hall directions do not name imported halls, and a hyphenated foyer label keeps its separate grid region classified as a linked foyer. Large unsupported enclosures inferred from bare lobby captions remain undetected rather than becoming oversized floor extensions.

A durable review URL allows reopening an interrupted review. Extraction runs in a worker with a five-minute timeout and stores progress after each page. Completed pages remain available if a later page or the worker fails. Jobs interrupted by server restart can be re-uploaded after the stale-job timeout. Uploading an old unsaved import after the reader version changes starts a new analysis rather than reusing stale detection; saved imports remain stable. Select **Start a fresh review** to re-import an already reviewed source.

Saved status is checked against live halls in the same organisation and venue whenever an import is opened, uploaded again, edited or saved. Deleted hall references are removed from the import record while preserving its reviewed geometry; surviving halls stay saved. Re-uploading a source after deleting its halls therefore lets the user review and recreate them, with new hall IDs. Repeated saves of surviving halls remain idempotent. Recreated halls need a new visual confirmation.

The Three.js top-down review supports source opacity, zoom/pan, movable polygon corners, redraw, new halls, foyer ownership, holes, restrictions/facilities, two-point metric calibration and dimension checks. A shared foyer has one source identity and hall links. Independent halls save separately or as a selected batch. Successfully saved halls cannot be changed indirectly by edits to their shared source; remaining independent halls remain editable.

Apply edits before opening the saved preview. Geometry, scale, boundary confirmation, restriction review and unclassified objects are non-overridable gates. Printed area, grid and dimension discrepancies need specific acknowledgements. The restriction-review checkbox confirms identified objects within the selected hall footprint; uncertain objects still need an explicit meaning. Unknown evidence is never displayed as passing. Existing hall updates require a matching version. Source checks and acknowledgements are saved with the floor version and audit record.

## Data and rendering

`PlanPage` uses original page coordinates, x right / y down. `FloorGeometry` uses metres, with a documented source origin and metric conversion. Polygons and holes are authoritative; grid pitch, origin and rotation remain independent. No automatic stretching to fit integer grid cells is performed. The renderer clips visible grid lines to region boundaries. Columns and other reviewed physical restrictions block their exact footprint; source markings alone do not block.

Reviewed halls keep the existing `floor/1` envelope with an optional `geometry/1` member. The POC hall viewer uses Three.js for this member and retains its previous renderer for historical rectangle-only floors. Source annotations such as gate text are visible in the source preview; they are not automatically promoted to saved objects. Facilities/restrictions can be added and named in the review.

Config export uses the provided `header/data`, `layout_data`, `legends`, `helper_text`, `exit_labels`, `direction` and `default_stalls` field names. Orthogonal masks and restrictions are decomposed into exact legacy rectangles; annotation positions use 20 pixels/metre. Non-orthogonal geometry or a grid the legacy renderer would stretch/shift sets `requiresGeometryRenderer: true`. The `geometry` extension remains authoritative. This does not modify `itpo_selfcare` or make its existing Fabric renderer support arbitrary polygons. Facility cards are extracted from source text and CAD symbols/layers; legend-table rows and dimension/stall labels are excluded from helper detection. Detected helpers retain source anchors, evidence and hall/foyer ownership. Confident helpers are included; uncertain OCR helpers require confirmation in **Labels and facility cards**, where text can also be renamed or hidden.

Saved floors store positioned `labels` and `iconGroups`. Whole annotation boxes are placed outside the hall and all its attached foyer/circulation polygons, with collision checks between annotations; annotation layout does not change floor geometry or scale. The Three.js preview and saved viewer show coloured facility icons and exterior captions, with a collapsible legend panel alongside the canvas. Export fills `helper_text` and `exit_labels` in the sample config's 20 pixels/metre coordinate system. North-arrow reconstruction from PDF linework remains unsupported; existing imported north metadata still renders.

The optional old/new diff compares drawable polygons at local top-left origins, with added/removed square metres and IoU. When imports have different crop origins or orientation, visual alignment must be checked; automatic registration is not implemented.

## Verification and limitations

`npm run eval:plans` runs analytical geometry tests and fixture extraction for both supplied PDFs, a generic millimetre DXF with 2 m grid, and a generic raster plan. The GitHub workflow runs this on pushes and PRs. Tests cover geometry holes, rotation, shared foyer identity, exact off-grid bands, source checks, legend-kind preservation and a detectable regression below 99% IoU. HTTP integration tests cover scoping, malformed input, optimistic review/version checks, partial commits and retries. Real worker uploads exercise Hall 14 review and saving with its foyer, restrictions and exterior annotation boxes, plus independent saves of four CAD halls with their named foyers.

CAD extraction runs in an isolated worker so its pinned PDF.js 3.11 reader cannot share the renderer's PDF.js 5 worker globals. A printed grid note calibrates CAD line families independently, allowing separate hall/foyer origins; scale is not inferred by assuming 1 m. Boundaries remain snapped to source CAD lines rather than stretched to nominal cells. Detached foyers are retained, and their footprints stay separate from all hall interiors. The generic reader remains the fallback when no calibrated CAD grid is available or hall identities disagree.

The PDF fixtures verify identities: 12/12A contains two halls; 8/9/10 contains four halls including 11. The dense CAD PDF fixture uses main's CAD engine for four separate hall floors (5, 4, 3, 2) and their restrictions; source foyer/circulation proposals retain separate roles and hall ownership. Dense pages retain selectable text even when path extraction is skipped. Raster grid detection uses stroke centres to avoid mistaking the two edges of one grid line for separate cells. Foyer ownership prefers matching source hall numbers; proximity is used only when labels do not identify an owner.

These fixtures do **not** constitute independently approved geometric truth. Raster grid envelopes are explicitly labelled proposals and remain unconfirmed. Grid-envelope and nearest-boundary detection can miss perimeter cells, choose an internal foyer line or miss a facility. Review and correction are required. Raster OCR is English; other languages remain visible in the source and can be named manually. OCR noise, clipped PDF paths, complex DXF blocks/bulges/hatches and approximated curves may need a vector-PDF re-export or manual tracing. This implementation does not claim universal automatic 100% accuracy. Human-verified geometry fixtures for the rest of the venue collection are still required before claiming a 99% regression guarantee for those plans.

## Running

Node >=20.16 (22 recommended). Run `npm ci` in backend and frontend, then restart the backend so its normal startup migrations apply the floor-plan, JSON provenance and reader-version schema changes. No LLM credentials or remote OCR service are required. A WebGL-capable browser is required for the review. Installing Poppler (`pdfinfo` and `pdftoppm` on PATH) enables an independent rendering fallback when PDF.js cannot render a document; without it, successfully read pages remain available and unread pages show a warning. Use `npm run build`, `npm test -- --runInBand`, `npm run eval:plans`, and the dedicated local test database for `npm run test:e2e -- --runInBand`. Never point integration tests at a production database.
